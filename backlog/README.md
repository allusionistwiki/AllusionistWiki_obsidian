# Backlog（追加機能・要望・着手中仕事の受付箱）

ユーザーから「追加機能・改善要望」の指示を受けたら、**このフォルダに 1 件 1 個の `.md` ファイルを作成して保管する**。セッションが途切れても残るように、CLAUDE.md（§9）から毎セッション読み込まれる。

## 保管の対象（2 種類）
1. **未着手の要望**：ユーザーから受けた追加機能・改善要望。
2. **着手中の仕事**：複数のセッションにまたがる作業（例：仮 CH の順次変換、ch220 までの episode 生成）。セッションが途中で切れても「どこまでやったか・次は何をするか」を回復できるように、**進捗を都度このファイルに記録する**。

## ステータス
- `pending` — 未着手
- `in-progress` — 着手中（進捗欄を都度更新）
- `done` — 完了（ファイルは直ちに削除。`wiki/log.md` に記録）

## 運用ルール
1. **作成**：ユーザーの指示内容をそのまま（＋受け取った日付）ファイル化して保管する。
   - ファイル名：`YYYYMMDD_<短い英語スラッグ>.md`（例：`20260926_export_api.md`）
   - 同名が既にあれば `-2` を付けて連番にする
2. **内容テンプレート**：
   ```markdown
   # <要望・仕事の要旨>
   - 受付日: YYYY-MM-DD
   - ステータス: pending
   - 出典: ユーザー指示（原文をそのまま記載）

   ## 指示原文
   > <ユーザーの発言を verbatim で引用>

   ## 補足・制約
   - <分かっている範囲で記載>

   ## 進捗（着手中の場合・都度更新）
   - YYYY-MM-DD HH:MM: <何をしたか・次の一手>
   ```
3. **着手中の記録（重要）**：作業を進めるたびに**進捗欄に 1 行追記**する（日時＋やったこと＋次の一手）。セッションがいつ切れても、このファイルを読めば続きから再開できることを目標にする。特に以下は必ず記録する：
   - 完了した区切り（例：変換済みの話数範囲、生成済み episode 一覧）
   - 未完了の残り（例：残りの話数、未コミットの差分）
   - 判断が必要な未決事項・ユーザー確認待ちの点
4. **再開**：セッション開始時・コンテキスト圧縮後にこのフォルダを確認し、`in-progress` の件は**進捗欄の最後の行から再開**する。`pending` の件は作業に取りかかる（他の作業との優先順位はユーザーに確認）。
5. **削除**：対応が完了したら**そのファイルは削除する**（残さない）。完了時は `wiki/log.md` に 1 行追記して記録する（例：`backlog/20260926_xxx.md 対応済み・削除`）。

## 注意
- `done` のファイルは残さない（削除済みのはずで、残っていれば処理漏れ）。
- 作業中の中間成果物（ダンプ・一時スクリプト）は置かない（`_temp/` へ）。backlog に残るのは**指示・計画・進捗の記録のみ**。
